# Solana x402 service boundary

The integration uses `@x402/core`, `@x402/svm` and `@x402/express` version
2.30.0, with `@solana/kit` 8.6.0. `service/x402.mjs` uses the SDK's V2 header
codecs, schema validation, SVM transaction builder and resource-server lifecycle.
It does not implement a proprietary payment header or replace x402 with an
ordinary token transfer.

## Runtime contract

`createGateway(config, {fetch?, rpc?})` accepts fixed deployment configuration:
`network`, `rpcUrl`, `facilitatorUrl`, `merchantOrigin`, `merchantPayTo`, `asset`,
`assetDecimals`, `amountAtomic`, `paymentEnabled`, `payerPrivateKey`,
`requestTimeoutMs`. Only the Solana Devnet CAIP-2 identifier is allowed. The key
is a server-only 64-byte Solana keypair, encoded as base64 or a JSON byte array.
The public login wallet does not imply ownership of this configured service
wallet or claim that it has test funds.

- `readiness()` checks local configuration/key parsing and reports public payer
  address even when signing is disabled. It does **not** prove RPC availability,
  facilitator compatibility, token accounts or funding.
- `quote(url)` requires an actual HTTP 402 challenge at the configured origin,
  exactly one approved exact/Devnet payment option, and exact resource binding.
- `sign(quote, {beforeSign})` requires an explicit final callback. The callback
  runs after RPC preparation and instruction checks, immediately before the
  private key signs. The caller must already have persisted an atomic purchase
  claim, and must recheck owner/approval/expiry within this callback.
- `redeem(url, signed, quote)` sends the original payload once, does not redirect
  and never signs or creates another payment. Its result keeps payment and
  delivery separate. A 200 response alone never establishes payment.
- `reconcile(signature, signed, quote)` checks Devnet genesis, a confirmed or
  finalized signature status, successful transaction metadata and the exact
  original transaction message bytes. When the facilitator receipt was lost,
  the lookup is bounded to 25 recent payer transactions. Failure to locate a
  matching transaction remains UNKNOWN; it is not proof of nonpayment.

SVM exact payloads are partially signed: the facilitator adds the fee-payer
signature later. Thus `sign()` generally returns `signature: null`, not an
invented transaction ID. The private saved object includes `paymentHeader`,
`messageHash`, `payer`, `requirements` and `resourceUrl`. Store the entire object
in the private database and exclude it from HTTP snapshots, prompts and logs.

The signer restricts the transaction to the SDK's version-0 compute-budget
instructions, one exact TransferChecked between the expected associated token
accounts, and one memo bound to the complete resource URL. New quotes use the
43-byte Base64url encoding of the full SHA-256 digest to fit the SDK's 20,000 CU
budget. Existing hex-encoded proofs can be reconciled and retrieved from a saved
receipt under matching merchant and facilitator terms. The merchant rejects new
settlement using that older format. The RPC genesis and mint decimals are checked
before signing. SDK RPC preparation has no exposed
abort option; a deadline guard disables the final signing callback so delayed
RPC completion cannot sign after the deadline.

## Merchant and recovery

`mountMerchant(app, {config, reportProvider, receiptStore, rpc?})` registers
`GET /merchant/reports/:resourceId?wallet=...&start=...&end=...`. Startup is lazy;
missing configuration does not falsely make the service ready. The returned
`initialize()` performs read-only facilitator discovery when explicitly called.

The report is prepared before settlement. It receives an AbortSignal bound to
the merchant request's total deadline and premature client disconnect. An
aborted report cannot start a settlement claim, including if a provider
ignores cancellation and returns late. Cancellation remains active while an
asynchronous claim or pending-receipt write is in progress, with a final check
after each write. If a claim completed after cancellation it remains durably
PENDING, without settlement or permission to create a replacement payment.
Once the SDK settlement call begins, client disconnect cannot cancel settlement
bookkeeping or erase its outcome.
The private receipt store provides
`get(key)`, `put(key, value)` and atomic `claim(key) -> boolean`. PENDING records
contain `resourceUrl`, `messageHash`, `payer`, and the serialized report `body`.
The record is saved before a settlement call. After independently checking the
chain outcome, it gains `status: SETTLED` and the SDK settlement `response`.
The exact saved body can then be returned for the same proof without another
settlement. A PENDING record never expires or becomes permission to charge
again. Recovery reobserves the original transaction rather than signing anew.

The upstream HTTP facilitator client follows redirects. This service subclasses
its transport to use bounded requests and `redirect: error`; raw provider/SDK
errors, payloads and credentials are not returned as diagnostics.

## Executed validation

`node --test test/x402.test.mjs` exercises actual SDK construction, local Ed25519
signing, genuine loopback 402/paid-resource HTTP, and deliberately scripted
facilitator/RPC outcomes. It covers changed terms, final approval rejection,
wrong genesis/decimals, concurrent identical proofs, signature tampering,
settlement failure, lost receipts, cached recovery, provider failure, deadlines,
redirects and malformed responses. These checks do not prove an external Devnet
settlement, funded account, public deployment or live user wallet approval.
